How pi-gui works

Where the agent lives, how the chat updates and what to change for GPUI.

pi-gui 1.0.1 · local build

The agent runs inside the Electron main process

React draws the window. DesktopAppStore runs the app. PiSdkDriver calls pi directly through the SDK, without a separate CLI process.

Key boundary: the interface has no direct access to Node.js. Commands go through preload and validated IPC handlers. The agent, extensions and app management share the main JS process.

History on disk and the chat on screen are different things

pi stores a tree of events. DesktopAppStore builds a view of it for the interface, and the renderer receives separate snapshots of state and the transcript.

Two data owners

pi: history and model context~/.pi/agent/sessions/…/*.jsonl
Messages, tool results, branches, compaction. Managed by SessionManager.
pi: settings and model access~/.pi/agent/
Including settings.json, models.json, auth.json. A project adds its own resources from .pi/.
pi-gui: app stateElectron userData/
catalogs.json, ui-state.json, scheduled-tasks.json, attachments and checkpoints.

The catalog stores the session list and file paths. It does not replace the JSONL history. The selected chat can differ between windows; WindowOwner handles that.

The model sees the active branch

Switching branches keeps the old entries. Compaction puts a short summary into future model requests and keeps the original history.

When switching chats: the UI changes the selection first and loads the transcript afterwards. sessionId and revision checks protect against stale responses. A new client has to keep this logic.

What to check first

1. Copying and IPC

On every text delta, main copies the transcript array and searches for the active message. A batched publish sends the whole transcript of the selected chat, not just the new text.

2. Markdown and geometry

Changed text goes through a synchronous Markdown parser in full. ResizeObserver measures row heights; a width change triggers flushSync and another layout.

3. A shared main process

The SDK, extension handlers and the store run in one JS process. Heavy synchronous work there delays command handling. Its share still needs measuring.

Search changes how rows render

Blue cells are rows in the DOM. In search mode the code takes the whole layout instead of visibleRows. That can sharply increase rendering work.

The 60 cells are illustrative. This shows behavior, it is not a benchmark.

Moving to GPUI removes React/DOM from the main interface. Copying history, expensive parsing and an overloaded event queue still need their own fixes. Using the GPU does not by itself explain or remove every delay.

Replace the interface, keep the pi engine

For a first prototype, separate the agent from the window. Below is the proposed architecture; current pi-gui has no such split.

Agent, models, tools, sessions and TypeScript extensions.
Commands over stdin, events over stdout.

pi already has RPC. To keep more of pi-gui logic, a custom Node host on top of PiSdkDriver is possible; its protocol, catalogs and task management would then have to be extracted from the app.

Can stay in pi

  • Agent loop and providersAuthentication, model requests, tool calls, retry and compaction.
  • JSONL sessions and resourcesHistory, skills and extension logic. Compatibility of their UI is checked separately.
  • Run lifecycleTreat work as finished on agent_settled. agent_end can be intermediate.

Needs to be built or adapted

  • Desktop featuresWindows, catalogs, background chats, schedules, Git, terminal and drafts do not come from pi RPC automatically.
  • Extension UIDialogs need an adapter. HTML panels live in a sandboxed iframe today; they need a webview or a new interface.
  • A new update pathA snapshot on open, then deltas. Bounded queues, a layout cache and parsing off the UI thread.

First test: open a long history, scroll it while the model generates and resize the window. Compare input latency, frame time and transferred data with pi-gui.
